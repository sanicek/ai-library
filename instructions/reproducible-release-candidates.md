# Reproducible Release Candidates

Use this policy for repositories that publish built packages or other installable
artifacts and require confidence that the tested bytes are the published bytes.

## Classify The Change

- A change is release-bearing when it changes shipped output, runtime behavior,
  compatibility, dependencies, or tooling that affects generated artifacts.
- Documentation, process, tests, and internal tooling do not require a release
  when shipped output is provably unchanged.
- Classify by resulting artifact behavior, not by source-file extension or label.
- For a release-bearing change, select the version and update required release
  records in the same pull request.
- Follow the repository's versioning policy. Do not infer that Semantic Versioning
  applies unless the repository adopts it.

## Build The Candidate

- Start from a clean, identified commit.
- Use the repository's canonical packaging entrypoint and pinned dependencies.
- Record source revision, relevant dependency versions, tool versions, build
  options, and target platform details needed to reproduce the artifact.
- Produce the final candidate archive or package once and calculate a strong
  checksum such as SHA-256.
- Refuse to silently replace different bytes for an already accepted version.

## Validate The Exact Artifact

- Validate archive structure, metadata, and contents before installation.
- Install or deploy the candidate artifact without rebuilding it.
- Run automated checks against the installed candidate where practical.
- Perform the smallest representative manual smoke test needed to establish the
  release contract. Do not expand it into an exhaustive matrix without request.
- Record the exact checksum and test outcome. If any candidate bytes change,
  previous acceptance no longer applies.
- Do not merge while required candidate acceptance is outstanding. Use a draft
  pull request when that state must be visible.

## Merge And Publication

- After merge, prefer a fresh clone or worktree for reproduction. Otherwise use
  only non-destructive fetch and fast-forward synchronization of a clean default
  branch. Stop on dirtiness or divergence; never reset, clean, or implicitly
  stash existing work to prepare the release.
- Require the rebuilt checksum to match the accepted candidate. A mismatch must
  be investigated and the final bytes validated again.
- Publish only the accepted installable artifact, its checksum, and the required
  release notes or provenance records.
- Immediately before upload, recompute the checksum of the exact file supplied to
  the publication command and compare it with the accepted checksum. Stop on any
  mismatch.
- Where the destination exposes an immutable digest, verify the published digest
  after upload and record it with the release evidence.
- Treat repository snapshots generated by hosting services as source archives,
  not automatically as supported installable packages.
- Keep tagging, release creation, deployment, marketplace upload, and other
  publication steps behind current user authorization and the repository's
  explicit policy. If either is unclear, stop and ask.
- Report the source revision, artifact identity, checksum, validation evidence,
  and publication result.
